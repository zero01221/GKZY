## ① 一句话结论

**不存在「下载一个库就能拿到 2017–2026、四表、31 省全齐」的单一数据源。** 但有一个决定性的好消息：当前库「专业录取分 / 招生计划只有 2023–2025」**不是源数据缺失，而是项目自己用 `--min-year 2023` 主动裁剪掉的**；从**已在用的同一个免费源** GaokaoCompass 重新构建、把裁剪参数改为 0，就能把 2017–2022 两张表补回（预计各增加约 1.3 倍行数）。剩下真正补不回来的，是数据集本身就没有的省年（2022–2025 四表齐全实际只有 107/124 个省年，不是宣称的 124/124）和 2026 当年数据。

当时需用户拍板；**2026-11-19 用户已明确授权「下载，只要数据库是全的就可以」**，执行结果见 §⑧。

## ③ GaokaoCompass「宣称全覆盖 vs 库里不全」的根因诊断

### 1. 数据集确实存在，且项目用的就是它（已核实）

- HuggingFace 直连在本环境不可达（`fetch failed`），但通过 WebSearch 索引到的 HF 页面、ModelScope 镜像页与 HF Bucket 镜像页三方交叉确认：数据集 `choucsan/Gaokao-Compass-11M` 真实存在，**License: MIT**，DOI `10.57967/hf/9882`，作者 Zhishan Zou，约 1.42 GB，最近一次上传约 4 个月前（相对 2026-11-19，即 2026 年 7 月左右），**无需登录即可下载**（公开数据集，项目脚本用镜像直连下载成功过）。
- 卡片数字：省份 31、年份 2017–2025、861 CSV、11,327,563 行；四表文件数 227/218/227/189，行数 5,862,063 / 4,497,048 / 763,558 / 204,894。
- 项目的 `tools/build_gc_db.mjs:23-28` 正是从 `hf-mirror.com/datasets/choucsan/Gaokao-Compass-11M/resolve/main/` 下载；`data/gc/filelist.json` **恰好 861 条**，按表统计 227/218/227/189，**与卡片逐项吻合**。结论：当前库本来就是该数据集的全量导入产物，不是另外一份数据。

### 2. 根因锁定：`slim_gcdb.mjs --min-year 2023`，不是导入过滤

证据链（四证合一）：

1. **filelist 里有 2017–2022 的 CSV，而且不小。** 按年统计（score-range / school-admission / major-admission / enrollment-plan）：
   `2017: 9/21/20/20`、`2018: 11/21/20/21`、`2019: 14/22/21/21`、`2020: 19/22/21/22`、`2021: 21/22/21/21`、`2022: 29/31/30/30`。
   例如 `data/2017/anhui/enrollment-plan.csv` 4,105,617 B、`major-admission.csv` 2,865,887 B。所以「源里没有 2017–2022 专业/计划数据」不成立。
2. **库内 `meta` 表写死了裁剪参数。** `高考志愿助手/data/gaokao.db` 与 `data/gc/gaokao.final.db` 均读到：
   `builtAt=2026-10-18...`、`minYear=2023`、`dropVocational=false`。
3. **代码直接对应。** `tools/slim_gcdb.mjs:126-134`：
   ```js
   const BIG_TABLES = new Set(['major_adm', 'plan_code']);
   const keepYear = (y, table) => {
     if (minYearAll && y < minYearAll) return false;
     if (MIN_YEAR && BIG_TABLES.has(table) && y < MIN_YEAR) return false;
     ...
   };
   ```
   `score_range` / `school_adm` 不受此过滤，恰好解释了「一分一段和投档线有 2017 起，专业和计划只有 2023 起」。
4. **提交说明自我印证。** `0074ce9` commit message 原文：「一分一段与院校投档线保留**全部 2017-2025**；专业录取分与招生计划保留**近三年**……需要全量：`node tools/slim_gcdb.mjs --min-year 0`」。

**结论：属于任务书中假设 ③（导入/建库阶段的年份限制），但精确位置是建库之后的 slim 阶段，而非 `build_gc_db.mjs` 的 `handleMajorAdm` / `handleEnrollment` 的 `continue`。** 这两个 handler 的 `r.length < 10/12`、`!name || !mname` 过滤对 2023–2025 数据显然是通过的（库里有 167 万 / 178 万行），不是主因。

**能否靠重跑直接补回：能。** 但注意两个前提：
- 本地 4 个 250MB 级 DB **都不是未裁剪的全量库**（均无 `_progress` / `_files` 表，`meta.minYear=2023`），必须重新下载 861 个 CSV（约 1.35 GB，构建期联网）并重建，再 `--min-year 0`。
- Git 历史里 4 个快照（`0074ce9` / `746c8ec` / `7daf88f` / `b28cd18`）我逐个在内存中解压核对过 `meta`，**全部是 `minYear=2023`**，所以「从旧版本找回」这条路已排除。

**预估收益与代价**：2017–2022 的 major/plan CSV 体积约为 2023–2025 的 1.34 / 1.29 倍，故 `major_adm` 约 167 万 → 350–400 万行、`plan_code` 约 178 万 → 370–420 万行（粗估，实际受去重与过滤影响）；未压缩库可能由 250MB 增至 400–500MB，Brotli 包可能由约 52MB 增至 90–130MB。**体积/性能是否可接受须用户拍板。**

### 3. 数据集的「31 省 × 2022–2025 全覆盖」宣称自相矛盾（已核实，属假设 ①）

- 卡片 Overview 写「四表齐全省份/年份：2022–2025 年 31 省全覆盖」；
- **同一份 README 的「2025 Coverage」表却写**：28 provinces 四表齐；青海 ✅❌❌❌（只有招生计划）；山西 ✅✅❌✅（缺专业录取）；西藏 ✅✅✅❌（缺一分一段）。
- 用 `filelist.json` 实测逐省年统计，四表齐全的「省年」数：

  | 年份 | 有任意数据的省 | 四表齐全的省 | 理论上限 |
  |---|---|---|---|
  | 2017 | 21 | 9 | 21 |
  | 2018 | 21 | 11 | 21 |
  | 2019 | 22 | 13 | 22 |
  | 2020 | 22 | 18 | 22 |
  | 2021 | 22 | 19 | 22 |
  | 2022 | 31 | **27** | 31 |
  | 2023 | 31 | **25** | 31 |
  | 2024 | 31 | **27** | 31 |
  | 2025 | 31 | **28** | 31 |

  2022–2025 合计 **107/124**，不是宣称的 124/124。即使导入做到 100% 无损，也补不出这 17 个缺口。

**结论：数据集描述夸大/前后不一致；项目库的部分缺口源于数据集本身，不是项目丢数据。** 另有藏区/青海等省份结构性缺表，属于高考数据公开的客观边界。

### 4. 少量「有 CSV 却入库 0 行」的单元格（未能完全核实，如实标注）

交叉核对 filelist（拼音省名→标准省名）与库内 `SELECT y,p ... GROUP BY y,p`：
- `score_range`：山东 2019–2024、福建 2023、海南 2024 共 8 个省年有 CSV 但 0 行；
- `school_adm`：湖北 2017/2021、河南 2023、上海 2024、云南 2024、江西 2024 共 6 个省年有 CSV 但 0 行；
- 质量报告显示这些单元格 `rows=0` 但部分 `baselineRows` 非零（如福建 2023 score_range baseline 965、上海 2024 school_adm baseline 1315），说明是「本该有」却没进来。

查 filelist 里的文件大小给出线索：`data/2020/shandong/score-range.csv` 与 `data/2023/shandong/score-range.csv` **只有 176 B**，`data/2024/shanghai/school-admission.csv` **353 B**，`data/2023/henan/school-admission.csv` **1,682 B** —— 基本是空壳或只剩表头，重跑也补不回。但福建 2023（23 KB）、海南 2024（15.8 KB）、山东 2022（12.9 KB）有实质内容却 0 行，**疑似列头与 `idx(h,'score')` 等硬编码字段名不一致，或 `score` 列整列无法 `int()` 转换**。

**本次严格遵守「不联网下载数据」，未拉取这些 CSV 样本验证，故记为「未能核实」**；若用户批准 A 层重建，建议顺带抽样这几个文件的表头再决定是否调整 handler（这是唯一可能需要改代码的点，需另行拍板）。

### 对用户原问题的诚实回答

> 「能不能帮我找到全的数据库？」

- **单一全量源：没有。** 没有任何一个免费或付费源能一次性给出「2017–2026 × 31 省 × 四表」。
- **「2017–2025 四表 31 省全覆盖」是否现实：不现实。** 现有免费源实际只有 107/124 个省年齐全；付费源的批次/院校/专业线也未必覆盖四表（CnOpenData 就缺一分一段）。西藏 2017–2026 全缺是结构性边界。
- **现实上能补到什么程度（调研时估算，已被实测修正）：** 原估「完整率升至 85%+」不成立——
